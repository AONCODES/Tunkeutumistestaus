## Artikkelit
### OWASP Top 10:2021

Kirjoitus hetkellä [sivut](https://owasp.org/Top10/A01_2021-Broken_Access_Control) eivät eivät toimineet (kokeiltu eri selaimilla, "page not found, sekä githubissa myös sivut alhaalla)", joten käytin Clauden tekoälyä ja laitoin hakuun "OWASP Top 10:2021, A01:2021 – Broken Access Control (IDOR ja path traversal ovat osa tätä)" (OWASP).
- Pääsynhallinta varmistaa, että käyttäjät toimii oikeuksiensa puitteissa, tämän epäonnistuessa tieto voi luvattomasti paljastua, sitä voidaan muokata tai tuhota.
- Path travelsarissa hyökkääjä muokkaa URL:ia tai polkuparametria päästäkseen tiedostoihin.
- IDOR, toisen käyttäjätilin katselu tai muokkaamisen salliminen antamalla sen yksilöllinen tunniste eli esim. blabla.fi/accountID_1234 vaihdetaan ID numeroon 1235 niin voidaan nähdä toisen käyttäjän tiedot ilman tarkistusta.

### PortSwigger (IDOR, Path Traversal & Cross-site scripting)

Ylempänä saatiinkin jo tekoäly avusteinen vastaus siihen mitä IDOR ja Path Travelsar tarkoittaa, mutta PortSwiggerin sivuilta saatiin hieman lisätietoa.

- IDOR.
  - Access control haavoittuvuus (sovellus käyttää käyttäjän syöttämiä arvoja/tietoja objektien suoraan käyttämiseen)
  - Esimerkkeinä URL:in lopussa muokkaamalla teksitiedoston numeroa tai käyttäjän ID numeroa. [PortSwigger](https://portswigger.net/web-security/access-control/idor).

- Path traversal.
  - Haavoittuvuus, jossa voidaan päästä lukemaan mm. sovelluksen koodia ja dataa, back-end järjestelmien tunnuksia ja OS tiedostoja.
  - Päästään käsiksi serverin tiedostoihin, jossa sovellus pyörii.
  - Esimerkkinä verkkokauppa, jossa sovellus lataa kuvan sivustolle osoitteesta `<img src="/loadImage?filename=218.png">`, joka lukee palvelimelta tiedoston `/var/www/images/218.png`. Tuota polkua muokkaamalla voidaan saada erinäisiä tietoja. [PortSwigger](https://portswigger.net/web-security/file-path-traversal).
  
- Cross-site scripting (XSS).
  -  web security haavoittuvuus (hyökkääjä voi vaarantaa käyttäjien ja haavoittuvan sovelluksen välistä kanssa käymistä).
  -  Manipuloidaan haavoittunutta webbisivua niin, että se palauttaa haitallisen JavaScriptin käyttäjälle ja näin voidaan päästä käsiksi tietoihin.
  - "naamioidutaan" uhriksi ja voidaan tehdä mitä tahansa toimintoja mitä uhrikin pystyisi tekemään.[PortSwigger](https://portswigger.net/web-security/cross-site-scripting).

To solve the lab, perform a cross-site scripting attack that calls the alert function.``

Search funktiossa joku häikkä ilmeisesti, mutta en saanut ZAPpiin mitään järkevää näkyviin tuli vain

Nyt sain History kohtaan näkyviin myös oman hakuni. Sain auki html-koodin ja etsin sieltä hakuni, se näkyi tällaisena `<h1>1 search results for 'shopping'</h1>`.

Kokeilin laittaa hakukenttään seuraavaksi ohjeistetun alert funktion `<script>alert</scrip>` mutta, en huomannut mitään erikoista. Googlen haussa tuli heti ensimmäisissä otsikoissa jo selväksi että alertin perään pitää lisätä jotain. Lisäsin sanan (´test´). Ei taaskaan mitään. Tässä harjoituksessa siis haku ei enkoodaa ollenkaan merkkejä joten pystyy kirjoittamaan scriptin hakukenttään. Hyökkäys löytyi kun ensiksi laitoin haku kenttään eri sanoja. ZAPissa näin html-koodin ja hakukentässä näkyi suoraan kirjoittamani haku sellaisenaan. Kävin toisella sivulla katsomassa miltä haku näyttää ja siellä erikoismerkit oli muutettu `content="Haku: 1 tulos hakuehdolla &quot;moikka moikka&quot;">`. Erikoismerkkejä ei siis enkoodattu Labsissa ja scriptin pystyi ajamaan.

### [Stored XSS into HTML context with nothing encoded](https://portswigger.net/web-security/cross-site-scripting/stored/lab-html-context-nothing-encoded)

`This lab contains a stored cross-site scripting vulnerability in the comment functionality.
To solve this lab, submit a comment that calls the alert function when the blog post is viewed.`

Hieman samanlainen tehtävä, alert funktio käynnistyy kun blogi postaus on luettu/avattu. Tämä meni läpi, mutta en ihan varma tuosta "calls the alert function when the blog post is viewed.". Kommentoin itse aluksi, mutta ZAP:iin en saanu näkyviin omaa kommenttiani, menin blogin normaalille sivuille ja sitten ZAPista näin html koodin ja siellä näkyi kommentit taas täysin ilman enkoodausta.

### Mitä hyötyä XSS hyökkäyksestä on?

Labseissa ajoimme Alert skriptiä, mutta hyökkääjä voisi käyttää myös jotain oikeasti haitallista scriptiä.
Perinteinen XSS exploitti on keksien (cookies) varastaminen. Voit syöttää varastamisen jälkeen keksit selaimeen ja päästä käsiksi kaikkeen mihin uhrikin olisi päässyt. [PortSwigger](https://portswigger.net/web-security/cross-site-scripting/exploiting)

## Path traversal

### [File path traversal, simple case](https://portswigger.net/web-security/file-path-traversal/lab-simple)

`This lab contains a path traversal vulnerability in the display of product images.
To solve the lab, retrieve the contents of the /etc/passwd file.`

Kokeilin tutkia ZAPissa ja selaimessa lähdekoodia, mutta en saanut millään tavalla haettua /etc/passwd. Löysin [youtubesta](https://www.youtube.com/watch?v=MT01x-vyCJU) videon, jonka avulla sain lopulta Labran ratkaistua. Ei toiminut siis ainakaan suoraan selaimessa jos muokkasi URL:in perään imagen tilalle uuden polun.

<img width="709" height="136" alt="Näyttökuva 2026-09-14 kello 0 24 36" src="https://github.com/user-attachments/assets/95b5ac55-65f9-4845-a367-fc7cbf81f2d7" />

Labran etusivulle mennessä ZAP:n historiaan tallentui useita GET-pyyntöjä, joiden joukossa oli kuvien latauspyyntöjä esim. `?filename=53.jpg`. Tästä näki, että sovellus lukee näytettävän kuvan suoraan järjestelmästä käyttäjän antaman tiedostonimen perusteella.

<img width="1197" height="129" alt="Näyttökuva 2026-09-14 kello 15 40 02" src="https://github.com/user-attachments/assets/529497a1-bd2a-4a84-9d28-2e729be0b3a5" />


Klikkasin ZAP:n historiasta kyseistä pyyntöä ja avasin sen Requesteriin (Ctrl+W), jossa pyynnön voi muokata ja lähettää uudelleen. Muutin filename parametrin arvon muotoon ../../../etc/passwd. Kolme peräkkäistä `../` siirtää luettavan polun kuvakansiosta juurihakemistoon asti, josta se etenee edelleen /etc/passwd-tiedostoon.

Lähetin muokatun pyynnön uudelleen. Vastaus (Response) näytettiin oletuksena kuvana, joten vaihdoin näkymän kuvasta tekstiksi `body: image → body: text`. Tällöin vastauksessa näkyi tekstinä /etc/passwd tiedoston sisältö, mm. käyttäjätilit (esim. root) ja niiden oikeudet.

### [File path traversal, traversal sequences blocked with absolute path bypass](https://portswigger.net/web-security/file-path-traversal/lab-absolute-path-bypass)

`This lab contains a path traversal vulnerability in the display of product images.
The application blocks traversal sequences but treats the supplied filename as being relative to a default working directory.
To solve the lab, retrieve the contents of the /etc/passwd file.
`

Labran avatessa huomasin heti ZAPissa saman haavoittuvuuden kuin edellisessä kohdassa, eli kuvien filename näkyy sellaisenaan. Kokeilin samaan tyyliin `../../../etc/passwd` mutta se ei onnistunut, koska sovellus blokkaa travelsar sekvenssit (tehtävän annon mukaan). Tehtävä onnistui hieman vahingossa, koska kokeilin ilman noita sekvenssejä vain `/etc/passwd` ja tuloksena sain tiedoston sisällön.

Tämä kohta selittänee `but treats the supplied filename as being relative to a default working directory.` eli sovellus käsittelee annetun tiedostonimen silti, nyt vain suoraan käytännössä "avaa tämä tiedosto". 

### [File path traversal, traversal sequences stripped non-recursively](https://portswigger.net/web-security/file-path-traversal/lab-sequences-stripped-non-recursively)

`This lab contains a path traversal vulnerability in the display of product images.
The application strips path traversal sequences from the user-supplied filename before using it.
To solve the lab, retrieve the contents of the /etc/passwd file.`

Tässä kohdassa jo tehtävän antokin kertoo että sekvenssit poistetaan käyttäjän antamasta syötteestä ennen käyttöä. 

Kokeilin tähän samoja kikkoja kuin aikaisemmissa tehtävissä = tuloksetta. Laitoin Labran otsikon googleen ja sieltä tuli vinkkinä "non-recursively" eli sovellus ilmeisesti poistaa sekvenssit vain kerran. Kokeilin kaksi kertaa samoilla sekvensseillä mutta ei onnistunut. Pähkäilyn jälkeen katsoin vastauksen Labsin sivuilta. Aika simppeli ratkaisu :) eli oikea Response saatiin laittamalla tuplasekvenssi `....//....//....//etc/passwd`.
